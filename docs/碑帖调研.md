# 碑帖定位：调研

2026-10-24

第一期已经能在「先有行或列，再在其中切字」的前提下工作。碑帖里有一批材料仍然满足这个前提，另一批不满足。两条路分开做。

本文只调查定位：外框、列或行、阅读顺序。认字仍然后接。

## 1. 两种材料

| | 行列对齐的碑帖 | 手写帖 |
| --- | --- | --- |
| 典型物件 | 楷书碑、墓志、有界格或列距稳定的拓片 | 法帖、信札、手卷、立轴、对联、册页；行书到草书 |
| 字的位置 | 列距、字距接近常数；有时整页是格子 | 列可弯、可疏可密；题款、名款字号另起 |
| 墨迹 | 拓本底噪、泐损、栏线或界格线、收藏印 | 纸色和墨色分开；连笔、枯笔；朱印多在彩色扫描上 |
| 现有流水线会在哪一步失败 | 检测器把相邻列并成一条，或把界格线当成笔画。列若切对，现有的列内墨迹切分还能用 | 检测器给不出一条可靠的列。列错了，列内再切只会整列错 |
| 合适的定位单位 | 先列，或先格子，再格内一字 | 先单字，再把字收成列 |

手写本（第一期的 `manuscript`）介于两者之间：列大体还在，字大体还能分开。狂草和没有列心的帖子不归那一档。

## 2. 可以直接用的部分

### 2.1 行级检测：先换模型，再决定要不要新模块

当前 `detect.py` 没有指定 `Det.ocr_version`，用的是所装 RapidOCR 的默认检测模型。RapidOCR 已能在同一套 ONNX 接口里换检测权重，几何和切字都不用改。

[PP-OCRv5 的 server 检测模型](https://huggingface.co/PaddlePaddle/PP-OCRv5_server_det)在飞桨公布的检测分数里，「古籍文本」一栏是 0.676，上一代 server 检测是 0.473。这是文本行检测分数，不是单字框分数。RapidOCR 的模型表里对应 `ch_PP-OCRv5_det_server`，Apache-2.0。同一张表里还有 PP-OCRv6，但没有单独公布的古籍检测分数，先不把它当成更好的选择。

CalliReader 的补充材料里，在难例（草书、布局散）上微调后的 PP-OCRv4，整页识别的 F1 只有 0.293，并且顺序混乱。所以这条行级检测器适合列还在的拓片，不适合拿来切草书。

### 2.2 单字检测：CalliReader 的检测器，不是整页大模型

[CalliReader](https://github.com/LoYuXr/CalliReader)（ICCV 2025，罗宇轩、连宙辉等）把整页书法拆成两步：一个只标「这里有一个字」的检测器，外加一个排序模块。识别和大模型理解是后一步，定位用不到。

检测器是在整页数据上微调的 YOLOv10，类别只有一个。公开权重在 [Hugging Face 的 `params/best.pt`](https://huggingface.co/gtang666/CalliReader/tree/main/params)，约 61 MB。补充材料表 S2 的检测分数：

| 子集 | IoU | 精确率 | 召回率 | F1 |
| --- | ---: | ---: | ---: | ---: |
| 易（楷书、字少、布局规矩） | 0.926 | 0.981 | 0.995 | 0.988 |
| 中 | 0.929 | 0.976 | 0.993 | 0.984 |
| 难（草书、布局散） | 0.898 | 0.978 | 0.830 | 0.898 |
| 未见过的 MTHv2 刻本 | 0.802 | 0.961 | 0.972 | 0.967 |

难例上精确率仍高，召回掉到 0.83：漏字多于多框。框是水平矩形，不是四点框。整页略斜时要先转正，再把矩形收成四点。

它在未见过的汉文大藏经上 F1 仍有 0.967，说明「单类单字检测」能跨到密集刻本。论文没有在拓片上报告结果。训练集来自雅昌和 CAOD 的书法作品，版式是匾额、方格、册页、立轴、中堂、对联、手卷，作者以近现代墨迹为主。这是手写帖的分布，不是碑拓的分布。

排序模块 OrderFormer 约 25 MB（`params/orderformer.pth`）。它先按间距和字号把字聚成列，并把名款从正文里分开，再给这些列排序。序列最长 50。列数不多、从右到左的拓片，现有的 `vertical_rtl` 已经做得到。对联、横额加落款，才需要这种排序。

CalliReader 的完整推理依赖 InternVL、CUDA 和 flash-attn，flash-attn 不支持 Windows。定位阶段只需要 `best.pt`。仓库本身没有许可证文件。数据集卡写的是 Apache-2.0。`best.pt` 若要随库分发，先核对模型卡；个人在样张上试跑可以现在做。

YOLOv10 的训练代码（[THU-MIG/yolov10](https://github.com/THU-MIG/yolov10)）和 Ultralytics 一样是 AGPL-3.0。hanloc 若要保持现在这种可随意安装的依赖，运行时只通过 ONNX Runtime 读自有权重，不把 Ultralytics 引进来。Apache-2.0 的同类检测器是 [RT-DETR](https://github.com/lyuwenyu/RT-DETR)，可导出 ONNX。它没有现成的书法权重，只作为以后自己训练时的许可更干净的骨架。

### 2.3 带单字框的整页数据

[CalliTrain](https://huggingface.co/datasets/gtang666/CalliTrain) 的标注里已经有每个字的 `shapes`：字头和归一化顶点，外加按列排好的释文。数据卡写 Apache-2.0。预览样本是对联、立轴、临帖，不是拓片。论文中的划分是训练 7,357 页、测试 3,192 页（即 CalliBench）。

[CalliBench](https://huggingface.co/datasets/gtang666/CalliBench) 同样 Apache-2.0，按易、中、难分层，适合以后验收单字检测，不适合当成拓片基准。

[SDAC-Det](https://tcliu.cc/publications/full-page-calligraphy-detection/)（ECCV 2026 VISART，刘天成等）公布了另一套整页书法检测基准：2,144 页、189,156 个字框、13 个来源，并强调切块时不要把一个字从中间切开。检索时还没有代码和下载地址。切块规则可以吸收，权重现在用不了。

下列数据只有单字图，没有整页坐标，不能训练定位：

| 数据 | 内容 | 许可 |
| --- | --- | --- |
| [MCCD](https://github.com/SCUT-DLVCLab/MCCD) | 约 33 万书法单字，带书体、朝代、书家 | 非商业，需申请 |
| [ARMCD](https://github.com/lhl322001/ARMCD) | 15,553 张残泐单字，来自碑帖，用于修复 | 以仓库说明为准 |
| [CASIA-AHCDB](https://nlpr.ia.ac.cn/pal/CASIA-AHCDB.html) | 约 220 万古代手写单字，来源是四库和佛经抄本 | 学术 |
| [zhuojg/chinese-calligraphy-dataset](https://github.com/zhuojg/chinese-calligraphy-dataset) | 约 13.8 万单字，19 位书家 | 以仓库说明为准 |

[MTHv2](https://github.com/HCIILAB/MTHv2_Datasets_Release) 有整页字框，但是刻本，而且仅供学术研究。第一期已经把它排除在再分发之外。CalliReader 用它做检测泛化测试是合理的；拿来训练并随库发布则不行。

### 2.4 几何方法：对齐拓片的主体

对齐拓片的公开实现很少，论文里的做法却一致，而且都能落在现有依赖上（NumPy、OpenCV）：

1. 局部阈值得到墨迹。Sauvola 按局部均值和标准差取阈值，比整页一个阈值更能对付拓本深浅不匀。`scikit-image` 里有现成函数；也可以在库内用积分图写一小段，避免为这一个函数加依赖。宾夕法尼亚大学的 [古籍竖排脚本](https://github.com/Ifena-Xia/paddleocr-htr-ancient-chinese) 已把 Sauvola 当作可选预处理，许可上只是脚本，吸收做法即可。
2. 去掉又长又直的线。界格、栏线在投影里会变成一整条墨。`cv2.HoughLinesP` 在已经依赖的 `opencv-python-headless` 里。快速线段检测器在 `opencv-contrib`，不必为它换包。
3. 按列投影切开，再在列内按间隙切字。列内这一步就是现在的墨迹切分。拓本噪声会让一行投影出现毛刺，字的左右结构也会在间隙处被拆开。公开文献里的补救是先平滑投影，再把明显窄于列宽的碎块并回去（例如专利 CN106503688A 描述的小波平滑，以及 2009 年用面积 Voronoi 合并构件的碑文切分）。这两份都没有可维护的代码。并块规则可以写在现有切分后面：窄于同列中位数一定比例的相邻块合并，合并后仍异常的保持 `uncertain`。
4. 界格若构成稳定格子，一格一字。空格留空，残格标不确定，不再沿墨迹去猜。

[open-guji-cv](https://github.com/open-guji/open-guji-cv)（Apache-2.0）对刻本做了「先版面、再逐列字符网格」，和上面第 3 步同构。它的预处理是书脊、边框、筒子页，对拓片用不上。作为库来依赖过重，作为「对齐页面用格子」的旁证足够。

### 2.5 印章、大图、古籍行分割模型

彩色扫描上的朱印可以用红色范围抹掉再检测。[yaodaoboy/remove_seal](https://github.com/yaodaoboy/remove_seal)（MIT）就是这条路。拓片上的收藏印通常是黑的，和笔画同色，红色规则无效。黑印先按「过大的团块」标成不确定，不在这一期做修复。[DocDiff](https://github.com/Royalvice/DocDiff) 能做印章去除和文档二值化，但是扩散模型，还要单独的印章权重，不适合装进定位库。

整页长边超过检测器上限时，小字会消失。第一期已在 `detect_lines` 留了切块注释。SDAC-Det 的补充规则是：块与块重叠，被切块边界截断的字框丢掉，只保留那个字完整落在某一块里的框，再映回全图。对齐拓片若在提高 `max_side_len` 之后仍然丢小字，再加这一步。

[Kraken](https://kraken.re/) 引擎是 Apache-2.0，能训竖排行分割。[CHAT 模型](https://github.com/colibrisson/CHAT_models)（CC BY-NC 4.0）的分割是为二值化的古籍书页训练的，类别是正文、天头、插图和双行夹注，输入比例 9:16。它服务刻本和抄本，不服务拓片和法帖。识别模型（16000 字、行图上准确率超过 99%）是认字，不进入这一期。

[Eynollah](https://github.com/qurator-spk/eynollah)（Apache-2.0）的行分割和二值化针对欧洲历史文献。权重不能直接用在汉字碑帖上。

甲骨拓片上的单类检测（[OBIMD](https://github.com/libang1991/OBIMD) 用 YOLOv11l，[LIU42/Inscriptions](https://github.com/LIU42/Inscriptions) 用 YOLOv8）只说明「拓本噪声里检测单字」这条路走通过。字形不同，权重不能搬。按原计划，甲骨仍在更后的阶段。

## 3. 建议的两条流水线

结果格式不用改。`Glyph` 的四点框、`uncertain`、一页多条 `Flow` 都已经够用。水平矩形写成四个角即可。

### 3.1 对齐碑帖 `stele`

沿用「先列、再列内切字」。

```
拓片
  → 轻度去底（局部阈值；若有又长又直的界格线，先抹线）
  → 行级检测，或在检测器并列时改用列投影
  → 列内墨迹切分（现有 split）
  → 过窄的碎块按同列字宽合并；仍异常的标不确定
  → vertical_rtl
  → 明显更大的一行（篆额、题名）单独成一条语流
```

先做的试验不写新模块：加一个版式，检测换成 `ch_PP-OCRv5_det_server`，关闭方向分类，长边上限高于刻本，框膨胀低于刻本，整页仍可先转 90°。用一张列距稳定的楷书碑、一张有界格的墓志看邻列是否粘连。粘连再写去线和列投影。单字检测器不作为这一档的第一选择。

### 3.2 手写帖 `modelbook`

不再假设「列框已经切对」。

```
帖
  → 单类单字检测，得到水平矩形
  → 矩形收成四点框
  → 列大体还在的，用现有 vertical_rtl 收列
  → 横额、对联、落款按字号和位置分成多条语流
  → 宽于同页字宽中位数很多的框视为连笔，标不确定，不切开
```

先做的试验是在两三张帖上加载 `best.pt`，只看框，不接它的大模型。框若能盖住楷书和行书单字，再考虑把同一结构训成自有 ONNX，训练数据用 CalliTrain 的 `shapes`。草书漏字（表 S2 召回 0.83）接受为不确定，不在这一期用连笔模型硬切。

OrderFormer 先不接。列序用几何规则；对联和落款用多条语流加人工改序。它的 50 列上限也盖不住长手卷。

## 4. 这一期不做

- 不把 CalliReader 的 InternVL、CalliAlign 装进库。
- 不把 Ultralytics 或 YOLOv10 训练代码列为运行时依赖。
- 不把 Kraken CHAT、Eynollah、open-guji-cv 整库依赖进来。
- 不训练拓片专用检测器，除非对齐碑帖的几何路线在样张上站不住。
- 不修复黑印和泐损，只标不确定。
- 不认字，不用单字图数据集。

## 5. 建议的样张

每种一张就够判断该不该写对应模块：

| 用途 | 样张 |
| --- | --- |
| 对齐碑帖，行级检测是否够用 | 列距稳定的楷书碑一开 |
| 对齐碑帖，界格会不会把列粘住 | 有界格的墓志一开 |
| 手写帖，单字检测是否盖得住 | 行书、列还大致可辨的法帖一开 |
| 手写帖，连笔应保持整块 | 草书信札或手卷一开 |

样张仍放 `samples/`，不提交。
